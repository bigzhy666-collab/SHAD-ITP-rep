# SHAD 本机接口约定与前端接入说明

版本：V1.0（待实现约定）

日期：2026-11-08

适用：用户负责前端及接口接入，另一位开发者负责本地后端和模型封装。

## 1. 交付目标与文档效力

软件在用户电脑本地运行，数据、模型、任务、报告均可保存在本机。基础检测流程不依赖云服务器或互联网。本机 HTTP 是进程间通信方式，不意味着建设在线软件。

推荐首期运行结构：

```text
本机启动入口
  └─ 本地后端（仅监听 127.0.0.1）
       ├─ 提供已构建的 Vue 页面、图表与中文字体
       ├─ /api：数据导入、模型查询、检测任务和结果
       ├─ Python：加载本站模型并执行检测
       └─ 本地持久化目录：数据、模型注册信息、任务、报告和日志
```

首期可以由启动入口打开本机浏览器查看界面；是否封装桌面安装包不影响本约定。后端负责提供稳定的启动、停止和本地持久化方式，前端不直接读取 `.pkl` 或执行 Python。

本文分清两种内容：

- **仓库事实**：从现有模型代码、模型卡和前端代码直接读取的行为。
- **实施约定**：本地后端尚需实现的接口路径、JSON 包装、任务机制及数据校验。这些内容是本次给出的方案，不声称仓库已经具备。

本文确定本地运行和模型接入边界；现有 PRD 的页面交互继续有效。旧文档中的云端、多人权限设想不作为本期前置条件。本文不改变已确认的页面风格、图标和图表布局，也不表示已完成接入。

## 2. 本期范围与分工

### 2.1 P0：先打通真实异常检测

1. 查询本地服务状态、能力和已注册模型。
2. 建立管段与换热站的数据绑定，导入本站 CSV 并校验。
3. 查看原始监测值、质量问题及标准化后的单位。
4. 创建检测任务、查询状态、获取分数曲线和确认告警事件。
5. 无异常、缺数据、模型不匹配、失败重试和软件重启均有明确结果。
6. 任务及结果保存到本机，关闭界面不丢失已完成任务。

### 2.2 P1：AI诊断与报告的真实能力

- 现有模型没有提供可靠的具体原因、解决方案、归因权重或模型诊断置信度。不得用检测结果自动冒充这些能力。
- AI诊断保留单选/多选事件、过程证据、历史、备注、归档和 Word/PDF 的产品目标；真实原因分析服务尚需另外实现。
- 本期真实模式下可查看和导出“异常检测报告”，诊断部分明确为“尚未接入原因诊断能力”。已有演示诊断可以保留在独立演示模式，不与真实任务混用。
- 报告、备注和归档的本机后端持久化列为 P1。完成前，不宣称浏览器 localStorage 是正式软件的完整存档方案。

| 事项 | 本地后端开发者 | 前端及接入开发者 |
|---|---|---|
| 模型运行 | Python 环境、模型加载、版本登记、站点匹配 | 展示真实可用能力和版本 |
| 数据 | 导入、映射、单位/时间标准化、质量校验和持久化 | 导入表单、字段映射确认、问题列表和监测图 |

| 报告 | P1：报告快照、版本、备注及归档存储 | 复用现有 Word/PDF 生成逻辑，展示与导出同一快照 |
| 软件启动 | 本地服务、资源托管、持久化目录、启动停止 | 构建前端、服务不可用提示与连接恢复 |

## 3. 对象与模型必须正确关联

现有 UI 使用“企业 → 管网 → 管段”，而模型对象是**换热站的站内设备和控制系统**，不能直接等同为埋地管段检测。

本期增加 `stationId` 作为模型作用对象，保留原 UI 层级：

```text
企业 / 管网 / 管段（UI 业务上下文）
                 └─ 绑定换热站 stationId（模型对象）
                      ├─ 本站数据集 datasetId
                      └─ 本站模型 modelId + modelVersion
```

- 一个管段可以关联多个换热站；发起检测时必须选择一个明确站点。只有一个绑定时可以默认选中。
- 绑定用于组织数据，不代表模型能检测管道腐蚀、裂纹或定位泄漏。
- 没有绑定时禁用真实检测，提示“请先关联换热站与本站模型”；不能自动使用相邻站或德国示例模型。
- `stationId`、`datasetId` 和模型登记的站点必须一致。后端校验 UI 路径所属关系，不能只信任客户端提交的名称。
- 任务保存创建时的对象名称和关系快照，后续切换、改名不会改写旧任务。
- 示例 `M1_s7.pkl` 仅用于相应示例站点。国内站点须使用本站训练产物。
- `M1/M2` 是现有训练代码中的数据配置标签，不能作为所有国内设备的通用厂商分类。

## 4. 公共通信规则（实施约定）

### 4.1 地址、资源与本机访问

- API 前缀：`/api`；契约版本由运行状态接口返回 `contractVersion: "1.0"`。
- 正式运行由本地后端同源提供 Vue 构建产物和 API，前端使用相对路径，不写死端口。
- 后端仅绑定 `127.0.0.1`，不默认对局域网开放。端口由启动入口决定并打开实际地址；端口占用时给出明确提示。
- 开发时前端开发服务可代理 `/api` 到本机后端。当前 Vite 配置尚未增加代理。
- 首期不设置业务登录页和账号权限。浏览器来源与 Host 校验由本地服务处理，拒绝无关站点的写请求，不开放任意来源跨域访问。
- 模型、字体、脚本、图表和数据均从本机加载。未来外部大模型服务属于单独能力，不能作为离线检测的隐含依赖。

### 4.2 编码、标识与时间

- JSON 使用 UTF-8；属性用 camelCase，但模型标准测点名及模型输出字段保持原有 snake_case，减少误映射。
- ID 为后端生成的不透明字符串，前端不解析 ID 含义。所有版本标识不可原地覆盖。
- 时间使用带偏移量的 ISO 8601，如 `2026-11-08T08:00:00+08:00`，查询参数中的 `+` 必须编码；前端统一使用北京时间展示。
- 本期检测和样本查询使用闭区间 `[start, end]`，起始必须早于结束。分页边界不改变任务计算范围。
- 本地中国站点模型进入 pandas 特征构造前按 `Asia/Shanghai` 的墙上时间生成索引，避免日周期特征错位。不同来源的时区必须登记，示例站不得直接套用中国时区重算。
- 不接受 JSON `NaN`、`Infinity`；缺测值用 `null`。非有限模型输出视为计算错误，不能伪装为健康结果。

### 4.3 响应结构

所有 JSON 成功响应：

```json
{
  "requestId": "req-example-001",
  "data": {"id": "det-example-001"}
}
```

所有 JSON 错误响应：

```json
{
  "requestId": "req-example-002",
  "error": {
    "code": "REQUIRED_FIELD_MISSING",
    "message": "缺少必需测点：瞬时热功率。",
    "retryable": false,
    "details": [
      {"field": "p_net_meter_heat_power", "reason": "未找到对应列"}
    ]
  }
}
```

列表的 `data` 固定为 `{items, page, pageSize, total}`，页码从 1 开始，默认 20，最大 500。默认任务按 `createdAt` 降序，点数据按 `timestamp` 升序，事件按 `start` 升序；相同时间按 ID 稳定排序。非法分页参数返回 422，不能静默截断全量导出。

HTTP 200 为读取成功，201 为同步创建成功，202 为任务已持久化并接受执行，400 为请求格式错误，404 为记录不存在，409 为状态/版本/幂等冲突，422 为数据校验不通过，503 为服务能力暂不可用，500 为内部错误。

查询到失败任务仍返回 200 和 `status: "failed"`；查询接口失败不等于模型任务失败。

## 5. 数据输入与预处理

### 5.1 核心输入：直接来自模型卡

| 标准字段 | 含义 | 模型单位 |
|---|---|---|
| `outdoor_temperature` | 室外温度 | ℃ |
| `p_net_supply_temperature` | 一次侧供水温度 | ℃ |
| `p_net_return_temperature` | 一次侧回水温度 | ℃ |
| `p_net_meter_heat_power` | 瞬时热功率 | kW |
| `p_net_meter_flow` | 瞬时流量 | L/h |
| `p_hc1_return_temperature` | 二次侧采暖回水温度 | ℃ |
| `s_hc1_supply_temperature` | 二次侧采暖供水温度 | ℃ |
| `s_hc1_supply_temperature_setpoint` | 二次侧采暖供水温度设定值 | ℃ |

选填测点以模型训练产物所用字段为准，可包括生活热水、储水箱、阀门、水泵及运行模式。不认识的文本类别不能自行猜测编码；首期导入以数值测点为主。

### 5.2 导入约定

首期输入采用 CSV，不要求实时 SCADA。`POST /api/datasets/import` 使用 `multipart/form-data`：

- `file`：CSV 文件内容，不是前端随意填写的本地绝对路径。
- `manifest`：UTF-8 JSON 字符串，示例如下。`columnMapping` 对八个核心字段必须完整，原列不得重复映射至同一标准字段。

```json
{
  "name": "1号站运行数据",
  "stationId": "station-local-001",
  "timezone": "Asia/Shanghai",
  "encoding": "utf-8-sig",
  "delimiter": ",",
  "timeColumn": "时间",
  "columnMapping": {
    "室外温度": "outdoor_temperature",
    "一次供水温度": "p_net_supply_temperature",
    "一次回水温度": "p_net_return_temperature",
    "瞬时热功率": "p_net_meter_heat_power",
    "一次流量": "p_net_meter_flow",
    "二次回水温度": "p_hc1_return_temperature",
    "二次供水温度": "s_hc1_supply_temperature",
    "供水温度设定值": "s_hc1_supply_temperature_setpoint"
  },
  "sourceUnits": {
    "outdoor_temperature": "degC",
    "p_net_supply_temperature": "degC",
    "p_net_return_temperature": "degC",
    "p_net_meter_heat_power": "kW",
    "p_net_meter_flow": "m3/h",
    "p_hc1_return_temperature": "degC",
    "s_hc1_supply_temperature": "degC",
    "s_hc1_supply_temperature_setpoint": "degC"
  }
}
```

实施时必须完成：

1. 提供导入文件与映射预览。`STANDARD_ALIASES` 只能辅助预填；“供水温度”“回水温度”“热量”有歧义，必须让用户确认侧别和瞬时/累计含义。
2. UTF-8/UTF-8 BOM 为默认支持；声明其他编码但不支持时明确报错，不输出乱码。按实际文件解析分隔符。
3. 识别时间、排序、记录无效行及重复行。按现有映射函数的规则，相同时间保留第一行，返回删除数量；必须记录导入时区。
4. 显式转换单位：`m3/h × 1000 → L/h`、`W ÷ 1000 → kW`、`MW × 1000 → kW`。未知单位拒绝，不能按数值大小猜测。累计热量 kWh 不能直接当瞬时功率 kW。
5. 检测输入按站点时区重采样为 30 分钟，数值取均值，区间左闭右开并标记左端时间；原文件、清洗记录和标准化结果分别留存。
6. 不跨缺口插值。缺测、越界、非数值单独计入数据质量，不能直接当运行故障。
7. 本期接入校验：缺少核心列、核心列全部为空、核心列无效比例超过 80%、标准化后无有效行，数据集记为 `invalid`，不能创建检测。这是适配层新增规则；当前 `detect()` 没有完整实现这些校验。
8. 连续空时间格不作为有效模型观测。将间隔大于 30 分钟的输入分为连续块，分别执行检测和事件合并，防止跨缺口累计和合并告警；这是本期接入层的明确新增规则。

导入创建成功返回 201，数据集状态为 `ready` 或 `invalid`，并包含 `issues`。文件无法解析、映射结构非法时返回 422。`invalid` 数据集可用于核查问题，修正后重新导入创建新数据集，不覆盖旧任务的数据。

数据集至少保存：`id`、`version`、`stationId`、`name`、`status`、`timezone`、`createdAt`、`sourceChecksum`、`preprocessingVersion`、`start`、`end`、`rawRowCount`、`normalizedRowCount`、`columns`、`columnMapping`、`sourceUnits`、`issues`。每项 issue 包含 `code`、`field`（可空）、`count`、`message`、`blocking`。

`columns` 为 `{field, label, unit, validCount, missingCount, invalidCount}` 数组，unit 使用 `degC | kW | L/h` 等规范代码，label 供页面显示。时间范围和行数对应标准化数据；无有效数据时 start/end 为 null。新导入数据集使用新 ID、version 为 `"1"`，首期不原地修改。原始文件校验值用于追溯，不代表文件具有真实性认证。

### 5.3 与模型代码的区别及配置来源

- `map_columns()` 本身只做映射、时间处理、排序和去重，没有完成外部 CSV 的单位转换与 30 分钟重采样。不能仅调用它就宣称预处理已完成。
- `detect()` 不会自动为外部 CSV 执行独立的传感器质量检测流水线。是否接入 `quality.py` 必须在版本中明确，未运行的检查不得显示“已通过”。
- 训练代码有最少 500 行检查；模型卡建议至少 30 天正常数据。这两者均不能直接当作推理的最少行数限制。
- 当前 `train_station_model(tag, sid, ...)` 内部通过 `load_substation()` 读取 PreDist 目录，并非任意外部 CSV 的通用训练接口。首期由模型/后端开发者准备并登记本站产物；若要在软件中训练国内 CSV，还需改造训练数据入口，不能称为现成能力。
- 特征包含 24 小时差分及滚动信息。首期使用本次请求范围内的连续块，不偷偷追加历史数据；短窗口/每块起始的特征不足须返回 `FEATURE_CONTEXT_SHORT` 提示。以后采用历史预热必须升级预处理版本并记录实际计算范围。
- `detect()` 每次调用从 0 开始计算 criticality。本期是**批次检测**，每个连续块从 0 开始；不能逐页调用模型、不能宣称实现了跨调用持续监测。
- 默认 M1 `c_thr` 为 11，但模型卡示例显式使用 7；M2 最终方案和部分默认自适应配置也有差别。接口必须读取实际模型产物配置，不能照文案硬编码 7 或自适应状态。
- 首期不让前端修改已加载模型的阈值、特征集或持续性参数。未来如允许修改，应形成新配置版本和结果快照。

## 6. P0 接口目录

以下均为待实现接口；路径供后端直接采用。任务失败信息结构与公共 `error` 一致。

| 方法与路径 | 请求/查询 | 返回 data | 说明 |
|---|---|---|---|
| `GET /api/runtime` | 无 | 服务版本、契约、运行模式、能力 | 前端启动时读取 |
| `GET /api/stations` | `enterpriseId`、`networkId`、`segmentId`、分页 | 站点列表 | 按 UI 所属关系筛选 |
| `POST /api/stations` | 站点名称、编码、企业/管网/管段 ID、时区 | 站点记录 | 绑定模型对象；服务端校验层级 |
| `GET /api/models` | `stationId`、分页 | 模型元数据列表 | 不把模型二进制发给浏览器 |
| `POST /api/datasets/import` | file + manifest | 数据集与 issues | 按第 5 节；同步导入 |
| `GET /api/datasets` | `stationId`、分页 | 数据集列表 | 固定数据集版本 |
| `GET /api/datasets/{id}` | 无 | 数据集元数据与 issues | 用于导入校验结果 |
| `GET /api/datasets/{id}/samples` | `start`、`end`、`fields`、分页 | 标准化采样列表 | fields 为逗号分隔标准字段名 |
| `POST /api/detections` | 第 7 节请求 | 已接受的任务 | 202，先持久化再执行 |
| `GET /api/detections` | `stationId`、`segmentId`、`status`、分页 | 任务列表 | 历史查询，不受当前 UI 对象覆盖 |
| `GET /api/detections/{id}` | 无 | 任务、状态、错误 | 轮询和刷新恢复 |
| `GET /api/detections/{id}/result` | 无 | 结果摘要、模型快照、查询链接 | 未完成时返回 409 `RESULT_NOT_READY` |
| `GET /api/detections/{id}/points` | `start`、`end`、分页 | 逐点模型结果 | 查询完整计算结果，不再调用模型 |
| `GET /api/detections/{id}/events` | `start`、`end`、分页 | 确认告警事件 | 按区间相交筛选 |
| `POST /api/detections/{id}/retry` | 空 JSON `{}`，新幂等键 | 新任务 | 仅失败任务可重试；沿用旧快照 |

说明：现有组织管理尚无真实后端，企业/管网/管段的本机注册表需与前端已有组织记录一次性对齐，保留稳定 ID。此表不表示其他组织维护接口已实现；后端可先随本地数据交付该注册表。`POST /api/stations` 请求为 `{name, code, enterpriseId, networkId, segmentId, timezone}`，同一企业的站点 code 重复返回 409。

`/samples` 返回条目为 `{timestamp, values, quality}`；`values` 使用标准字段名，值为 number 或 null；`quality` 为同名字段到 `valid | missing | invalid` 的映射。单位从数据集 `columns` 元数据读取，不能由前端猜测。

### 6.1 运行状态示例

```json
{
  "requestId": "req-runtime-001",
  "data": {
    "serviceVersion": "0.1.0",
    "contractVersion": "1.0",
    "mode": "local",
    "capabilities": {
      "dataImport": true,
      "anomalyDetection": true,
      "causeDiagnosis": false,
      "reportPersistence": false,
      "offlineDetection": true
    }
  }
}
```

示例中的 true/false 表示首期目标，实际响应必须反映实际实现。前端应根据能力禁用未实现操作，并解释原因；服务不通显示“本机服务未启动或连接中断”，不显示“SCADA 掉线”。

### 6.2 模型登记信息

每个模型元数据至少包含：`id`、`version`（后端登记的不可变版本）、`artifactChecksum`、`stationId`、`name`、`purpose: "station_anomaly_detection"`、`isDemo`、`trainedAt`（未知可空）、`trainingTimezone`、`trainStart`、`trainEnd`、`scoreKind`、`featureMode`、`cyclic`、`adaptive`、`cThr`、`quantile`、`requiredFields`、`trainingFeatureColumns`、`status`（`ready | unavailable`）。

`requiredFields` 为接入要求的八个核心字段；`trainingFeatureColumns` 来自实际模型 `cols`。源文件没有版本号时，由注册层分配版本并关联校验值，不能编造训练日期。模型由后端预先登记可信的本地文件，首期不开放浏览器上传任意 `.pkl` 或任意路径加载。

## 7. 创建检测与任务生命周期

### 7.1 创建请求示例

Header：`Content-Type: application/json`、`Idempotency-Key: <本次提交唯一字符串>`。

```json
{
  "name": "1号站历史运行检测",
  "context": {
    "enterpriseId": "enterprise-local-001",
    "networkId": "network-local-001",
    "segmentId": "segment-local-001",
    "stationId": "station-local-001"
  },
  "datasetId": "dataset-local-001",
  "modelId": "model-local-001",
  "modelVersion": "1",
  "range": {
    "start": "2026-11-08T00:00:00+08:00",
    "end": "2026-11-08T08:00:00+08:00"
  }
}
```

请求不包含演示场景 `scenario`、前端倒计时 `readyAt`、自造阈值和候选原因。监测页所选显示参数不代表可以删减模型输入；模型使用本站完整核心字段。

校验：来源均存在且 ready、对象所属一致、模型适用本站和时区、数据单位及字段有效、范围合法且在数据集中、范围内存在有效点。校验不通过不创建任务；执行中才发现的数据错误记录为失败任务。

响应 202 的 `data` 至少包括：`id`、`name`、`status`、`createdAt`、`startedAt`、`finishedAt`、`phase`、`progress`、`contextSnapshot`、`datasetSnapshot`、`modelSnapshot`、`range`、`warnings`、`error`、`retryOf`。未发生的时间、错误、retryOf 为 null；快照冻结 ID、版本、名称、校验值、时区和实际算法配置。

快照的最小字段固定如下，查询任务和查询结果使用同一份：

| 字段 | 内容 |
|---|---|
| `contextSnapshot` | `enterprise: {id, name}`、`network: {id, name}`、`segment: {id, name}`、`station: {id, name, timezone}` |
| `datasetSnapshot` | `id`、`version`、`name`、`sourceChecksum`、`timezone`、`preprocessingVersion` |
| `modelSnapshot` | `id`、`version`、`name`、`artifactChecksum`、`stationId`、`isDemo`、`trainingTimezone`、`featureMode`、`scoreKind`、`cyclic`、`adaptive`、`cThr`、`quantile` |
| `range` | 实际请求的 `start` 和 `end`，带时区 |
| `warnings` | `{code, message}` 数组，无警告时为空数组 |
| `error` | null 或 `{code, message, retryable, details}`；运行失败不返回原始堆栈 |

### 7.2 状态、查询和重复提交

```text
queued → running → success
                 └→ failed
failed → 用户重试 → 新任务 queued（旧任务保留）
```

- `phase` 可为 `queued`、`validating`、`detecting`、`saving`、`completed`、`failed`；只在实际进入阶段时更新。
- 当前 Python 检测没有进度回调，`progress` 返回 null，前端显示阶段和耗时。不能根据等待时长模拟 66% 等数字。
- 前端每 1 秒查询当前可见的运行任务；页面隐藏可降至 5 秒。请求异常按 2/4/8 秒退避，恢复后重新读取状态，不重复提交任务。
- 对同一路由、同一幂等键和同一请求体重复提交，返回原任务，不重复计算。相同键而内容不同返回 409 `IDEMPOTENCY_CONFLICT`。幂等记录与任务一同持久化。
- 用户明确再次执行使用新键，创建新任务。重试接口复用原任务的冻结配置，不受当前全局对象影响。
- 软件关闭后不承诺继续计算。下次启动，未完成的 queued 任务重新排队；已开始但未完成的 running 任务标为 failed，错误 `TASK_INTERRUPTED`，供用户重试，不靠时间自动判成功。
- 先原子保存结果，再发布 success。进程中断不能留下 success 但没有结果的任务。
- 首期不提供取消、删除和模型在线训练接口，前端不展示对应的可用操作。

## 8. 结果格式与准确展示

### 8.1 逐点结果

`/points` 的成功响应示例（数值仅说明结构，不是实测结果）：

```json
{
  "requestId": "req-points-001",
  "data": {
    "items": [
      {
        "timestamp": "2026-11-08T03:30:00+08:00",
        "blockId": "block-001",
        "score": 2.4,
        "threshold": 1.8,
        "alarm": true,
        "criticality": 7,
        "health": 0.0,
        "confirmed": true
      }
    ],
    "page": 1,
    "pageSize": 500,
    "total": 1
  }
}
```

输出字段来自模型；`timestamp`、`blockId` 和分页包装由后端补充。语义必须保留：

- `alarm = score > threshold`；等于阈值不算超阈。
- criticality 从 0 开始，超阈加 1，不超阈减 1，下限为 0。
- `confirmed = criticality >= 模型实际 cThr`。因计数缓降，当前点 alarm 为 false 时，confirmed 仍可能为 true。
- `health = clip(1 - score / threshold, 0, 1)`（非正阈值的保护分母按当前代码处理）。健康度不是故障概率或诊断置信度；显示百分数时只是乘以 100。
- 当前模型是综合多变量分数，不能将其标为某个温度或压力的直接超限值。

### 8.2 确认告警事件

事件由每个连续块内的 `segments()` 形成。`/events` 的条目示例：

```json
{
  "id": "event-det-local-001-001",
  "detectionId": "det-local-001",
  "stationId": "station-local-001",
  "blockId": "block-001",
  "kind": "station_state_anomaly",
  "title": "换热站运行状态偏离正常水平",
  "start": "2026-11-08T03:30:00+08:00",
  "end": "2026-11-08T04:00:00+08:00",
  "hours": 0.5,
  "peak_score": 2.4,
  "max_criticality": 8,
  "affectedMetrics": null,
  "cause": null,
  "solution": null,
  "boundary": "within_range"
}
```

- 事件 ID 在保存结果时生成并持久化；翻页、刷新或查询筛选不能重新编号。
- `end` 是本次计算中最后一个 confirmed 点的时间。`hours` 与现有函数一致，等于 end-start，单点为 0 小时，不能私自加半小时。
- `affectedMetrics`、`cause`、`solution` 当前无法由该模型确定，返回 null；界面显示“综合状态异常 / 原因待诊断”，不能生成“压力下降”“阀门故障”等结论。
- `boundary` 为 `within_range | touches_range_start | touches_range_end | touches_both`，表示结果是否触及请求边界。触及结束不表示故障已经恢复，也不表示本次请求之外仍在持续。
- 数据质量问题另列，不进入事件勾选数量；压力单参数阈值事件属于独立规则检测器，未来需另标 `kind` 和算法来源，不由当前模型伪造。
- 没有 confirmed 事件时任务仍为 success，事件列表为空；点级 alarm 曲线仍可查看。

### 8.3 结果摘要

`/result` 的 `data` 至少包含 `detectionId`、`contextSnapshot`、`datasetSnapshot`、`modelSnapshot`、`range`、`computedAt`、`preprocessingVersion`、`summary`、`warnings`、`links`。

- `summary`：`pointCount`、`alarmPointCount`、`confirmedPointCount`、`eventCount`、`blockCount`、`qualityIssueCount`。
- `links`：本任务的 points 和 events 相对路径。
- warnings：`{code, message}` 数组，例如短历史、分块和缺失填补说明。
- 结果查询失败时保留已加载图表并提示重试；CSV 全量导出需遍历所有分页，任何一页失败则停止下载并提示，不能只导出当前页却标“全部”。

## 9. AI诊断与报告的后续接口边界（P1）

以下为后续约定，**不是本期模型已提供的功能**。`causeDiagnosis: false` 时，前端不发送真实诊断请求；若调用未启用的能力，返回 503 `CAPABILITY_UNAVAILABLE`。

| 方法与路径 | 后续用途 |
|---|---|
| `POST /api/diagnoses` | `{detectionId, eventIds}`，对一个检测任务中的一项或多项事件创建诊断 |
| `GET /api/diagnoses`、`GET /api/diagnoses/{id}` | 历史、状态、公开过程证据与诊断结果 |
| `POST /api/reports` | `{detectionId, diagnosisId, eventIds}`，diagnosisId 可空；创建报告快照 |
| `GET /api/reports`、`GET /api/reports/{id}` | 报告历史、版本与归档筛选、查看快照 |
| `PATCH /api/reports/{id}/note` | `{note, expectedRevision}`；未归档时保存备注 |
| `POST /api/reports/{id}/archive` | `{expectedRevision}`；原子保存当前版本并锁定 |
| `POST /api/reports/{id}/versions` | `{expectedRevision}`；依据相同来源创建新版本，不覆盖旧版 |

P1 实现时需要遵守的确定规则：

1. eventIds 非空、去重，全部来自同一个成功检测任务；诊断与报告的对象、模型、数据来源必须一致。跨站点/跨任务选择返回 422 `SOURCE_MISMATCH`。
2. 诊断输出至少区分 observations（已观察证据）、hypotheses（可能原因）、recommendations（核查与解决建议）和 limitations（局限）。置信度没有校准依据时用 null，不能沿用前端演示权重。
3. 过程展示只呈现实际步骤、公开证据摘要和实际计算图表，不伪造模型内部思考。不能把数据准备、异常检测完成标为“故障原因已确认”。
4. 报告保存独立来源快照、所选事件、检测结果、可选诊断结果、生成时间、版本、备注、归档时间以及 demo/真实来源标记。
5. 前端现有 docx/pdfmake 可继续负责生成文件，无需先增加后端导出接口。图表和中文字体均本地可用；Word/PDF 与页面读取同一个已保存报告版本。
6. 备注/归档使用 revision 乐观锁，冲突返回 409 `REVISION_CONFLICT`。归档版本不可改备注，重新生成必须创建新报告版本。
7. 导出前保存尚未保存的备注；保存失败则提示重试，不声称导出了已存档版本。字体、图表或文件生成失败不改变归档状态。
8. 在 P1 持久化完成前，旧演示报告仍可在演示模式导出；真实检测的阶段报告不混入演示原因和虚构处理建议。

| code | HTTP | 页面行为 | retryable |
|---|---|---|---|
| `INVALID_REQUEST` | 400 | 保留表单，提示请求格式有误 | false |

| `UNIT_UNSUPPORTED` | 422 | 标出单位，要求转换/确认 | false |
| `TIMEZONE_MISMATCH` | 422 | 标出数据与模型时区不一致 | false |

| `STATION_BINDING_REQUIRED` | 422 | 引导先关联站点 | false |
| `SOURCE_MISMATCH` | 422 | 保留选择，提示站点/来源不一致 | false |
| `MODEL_UNAVAILABLE` | 503 | 保留任务输入，提示登记可用本站模型 | false |

## 11. 前端接入改动清单（后续实施）

1. 增加独立 API 客户端：统一 base URL、JSON、错误映射和请求标识；演示与真实服务显式分开，真实服务失败不得静默回退演示结果。

3. 保留四类现有 UI 参数，但增加与模型八个标准字段的明确映射。不能将二次循环流量当作一次侧模型流量，不能用压力代替缺失的热功率和设定值。

9. 全局刷新与 Ctrl+R 重新获取数据和任务状态，保留路由、筛选、选择，不重建任务。
10. 生产使用已构建前端和本地字体；Vite 开发服务器不作为正式软件启动方式。

## 12. 联调验收清单

| 验收项 | 预期结果 |
|---|---|
| 无互联网启动 | 本机界面、模型、字体和已保存历史可用；能力未实现时准确标识 |
| 正常数据导入 | 八个字段、单位、时区、行数和质量报告可核查 |
| m³/h 输入 | 模型流量实际换算为 L/h；页面单位与数据一致 |
| 累计热量/歧义列名 | 不自动冒充热功率；映射错误可见且阻止检测 |
| 时间重复/非法/大缺口 | 清洗统计可见，缺口分块，不跨缺口合并事件 |
| 相同提交重复点击/超时重发 | 使用同一幂等键只产生一个任务 |
| 没有异常 | success，events 为空，不显示失败或虚构诊断 |
| 计数下降期 | alarm 可为 false、confirmed 仍为 true，UI 与原始输出一致 |
| 切换全局管段 | 旧任务、曲线和报告仍显示创建时的站点与来源 |
| 短历史 | 提示特征上下文不足，不伪造全天历史 |
| 模型不属于本站 | 请求被拒绝，不能强行套用示例模型 |
| 模型执行失败 | 失败记录、错误信息可查，重试创建新任务 |
| 服务重启 | 完成记录保留，queued 恢复，running 按 TASK_INTERRUPTED 处理 |
| 分页与曲线 | 翻页只读已保存结果；全量导出没有漏页或重新计算 |
| 原因诊断未接入 | 真实检测不出现演示故障原因、权重和解决方案 |
| P1 报告 | 同一快照导出中文 Word/PDF；备注、归档和历史版本可恢复 |

对照模型的联调方法：后端对**同一标准化数据连续块、同一模型产物**直接执行 `model.detect(df)`，与 API 逐点返回的 score/threshold/计数/布尔标记逐项比较；事件再与 `segments()` 比较。浮点比较使用合理数值容差，布尔、计数、时间和事件边界必须一致。此项由后端提供实际结果作为联调样本，不用手写固定异常替代。

## 13. 建议实施顺序与本轮状态

1. 后端先交付 `/runtime`、站点/模型登记、CSV 导入与查询。
2. 后端完成检测创建、状态、结果、事件、重试和本机持久化；提供一个有事件及一个无事件的可复现测试数据集。
3. 前端按第 11 节接入，先走通“选站点 → 导入 → 检测 → 曲线 → 事件 → 历史恢复”。
4. 双方按第 12 节验收真实检测，然后推进原因诊断能力及报告持久化，不将其与检测模型能力混淆。
5. 最后完成本机启动入口、停止行为及离线验证；安装包形式可在此基础上确定。

本轮仅新增和整理接口约定及文档入口，**没有修改模型、运行前端接入或实现 HTTP 服务**。不需要用户另行提供已经能从仓库确定的模型字段。待双方实施时仅核对本约定与实际后端返回是否一致。
